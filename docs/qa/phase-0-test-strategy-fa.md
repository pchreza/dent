# استراتژی تست و دیباگ — از فاز صفر تا تحویل

## 1. هدف

تست بخشی از طراحی است و نه فعالیت پایانی. تمام قابلیت‌های جدید باید تست قابل تکرار، دادهٔ نمونهٔ کنترل‌شده، مسیر بازتولید خطا و معیار عبور داشته باشند. تست‌ها با نام رفتاری و الگوی Arrange/Act/Assert نوشته می‌شوند.

## 2. هرم تست

| لایه | هدف | نمونه |
|---|---|---|
| Unit | منطق خالص و قواعد دامنه | تبدیل تاریخ، محاسبهٔ مبلغ، وضعیت درمان، تشخیص تداخل. |
| Feature | مسیر HTTP/Permission/Database | ایجاد بیمار، تأیید QR، ساخت فاکتور، تغییر وضعیت نوبت. |
| Integration | ارتباط ماژول‌ها و Provider | اعلان داخلی، Cron، فایل خصوصی، Job بکاپ. |
| Security | کنترل سوءاستفاده | Cross-Tenant، IDOR، Brute Force، XSS، CSRF، Upload. |
| Browser/Manual | RTL، ریسپانسیو و چاپ | فرم QR موبایل، تقویم، نمودار دندان، رسید A4/حرارتی. |
| Load | رفتار فهرست/جست‌وجو | فهرست بیماران و نوبت در دادهٔ بزرگ؛ ۱۰۰ کاربر هم‌زمان طبق توافق. |

## 3. گیت‌های اجباری فاز صفر

- [x] نیازمندی‌های ۲۰۰گانه تبدیل به MVP و فازهای اجرایی شدند.
- [x] نقش‌های قطعی و دامنهٔ مجوزها مشخص شدند.
- [x] مدل Tenant و سناریوی Cross-Tenant تعریف شد.
- [x] مدل دادهٔ سطح بالا و ایندکس‌های اولیه مستند شدند.
- [x] مدل تهدید و کنترل‌های امنیتی ثبت شد.
- [x] RTL و Design System اولیه تولید و معیارهای QA ثبت شد.
- [x] نصب، ارتقا، Cron و بکاپ به‌عنوان نیاز عملیاتی ثبت شدند.
- [ ] خروجی فاز صفر در Commit قرار گیرد و از نظر کیفیت متنی بازبینی شود.
- [ ] فهرست کارهای فاز یک از دل اسناد استخراج شود.

## 4. تعریف Done برای هر فاز

یک فاز فقط وقتی Done است که تمام موارد زیر انجام شده باشد:

1. کد و Migration مربوط در شاخهٔ پروژه قرار گرفته باشد.
2. تست Unit/Feature مربوط سبز باشد.
3. تست دسترسی و جداسازی Tenant انجام شده باشد.
4. تست RTL در عرض‌های ۳۷۵، ۷۶۸، ۱۰۲۴ و ۱۴۴۰ انجام شده باشد.
5. خطاهای بحرانی و شدید صفر باشد.
6. Migration و rollback بررسی شده باشد.
7. متن‌ها، ترجمه‌ها و راهنمای کاربری به‌روز شده باشد.
8. گزارش فاز با دستور اجرای تست و Known Limitations ثبت شده باشد.
9. Build/Install clean در محیط مشابه cPanel بررسی شده باشد.
10. نسخه برای آزمون پذیرش کاربر ارائه شود.

## 5. جریان دیباگ

برای هر خطا:

```text
Capture -> Reproduce -> Isolate -> Explain Root Cause -> Minimal Fix
-> Add Regression Test -> Run Relevant Suite -> Run Full Regression
-> Document -> Close
```

گزارش هر خطا باید علت ریشه‌ای، شواهد، مسیر بازتولید، فایل/کلاس، اصلاح، تست افزوده و پیشنهاد پیشگیری را شامل شود. اصلاحی که فقط پیام خطا را پنهان کند اما علت را حل نکند پذیرفته نیست.

## 7. سناریوهای مرجع پذیرش MVP

| ID | سناریو | انتظار |
|---|---|---|
| AC-01 | نصب تمیز روی cPanel | ویزارد همهٔ مراحل را اجرا و مسیر نصب را قفل می‌کند. |
| AC-02 | ساخت دو کلینیک | هر کلینیک داده و برند مستقل دارد. |
| AC-03 | تغییر ID بیمار از Tenant A به B | 403/404 امن و بدون افشای داده. |
| AC-04 | ثبت QR بیمار جدید | صف منشی ساخته و اعلان داخلی ایجاد می‌شود. |
| AC-05 | QR با موبایل/کد ملی موجود | رکورد تکراری ساخته نمی‌شود و پیام راهنما نمایش داده می‌شود. |
| AC-06 | تأیید و فعال‌سازی بیمار | حساب بیمار و اتصال Tenant صحیح ایجاد می‌شود. |
| AC-07 | هشدار حساسیت | در صفحات درمانی مربوط به بیمار برجسته و متنی نمایش داده می‌شود. |
| AC-08 | طرح درمان دوگانه | بیمار می‌تواند هم‌زمان دو طرح فعال مستقل داشته باشد. |
| AC-09 | نوبت متداخل | رزرو غیرمجاز رد و دلیل قابل فهم نمایش داده می‌شود. |
| AC-10 | پرداخت اضافه | مبلغ اضافه به کیف پول همان Tenant منتقل می‌شود. |
| AC-11 | تغییر قیمت خدمت | فاکتور/آیتم قدیمی تغییر نمی‌کند. |
| AC-12 | خروجی محدود | خروجی فقط دادهٔ مجاز و فیلترشده را شامل می‌شود. |
| AC-13 | ورود پشتیبانی | دلیل اجباری، Support Session و Audit ثبت می‌شود. |
| AC-14 | خطای فنی | کاربر پیام فارسی و کد پیگیری می‌بیند و جزئیات در پنل فنی می‌ماند. |
| AC-15 | بازیابی بکاپ | دادهٔ Tenant به محیط/وضعیت سالم برمی‌گردد و نتیجه ثبت می‌شود. |
