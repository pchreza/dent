# معماری فاز صفر — پلتفرم Disweb Dental SaaS

**وضعیت:** تأییدشده برای آغاز فاز یک

**هدف سند:** تبدیل تصمیم‌های محصول به قراردادهای فنی قابل اجرا برای یک سامانهٔ SaaS چندمستاجری مدیریت کلینیک دندان‌پزشکی.

## 1. تصمیم‌های اصلی

| موضوع | تصمیم |
|---|---|
| زبان سمت سرور | PHP 8.3 با Laravel؛ کد با `declare(strict_types=1)` و PSR-12. |
| رابط | Blade و Livewire/Alpine در حد تعاملات لازم؛ بدون SPA سنگین در MVP. |
| داده | MySQL 8 با یک دیتابیس مرکزی و `tenant_id` برای داده‌های کلینیکی. |
| فایل | مسیر منطقی جدا برای هر مستأجر؛ ارائهٔ فایل فقط از مسیر کنترل‌شدهٔ سمت سرور. |
| منطقه و زمان | `Asia/Tehran`، تقویم داخلی شمسی، ذخیرهٔ زمان در UTC در صورت نیاز به رویدادهای دقیق و نمایش محلی. |
| نصب | ویزارد وب‌محور، قابل اجرا روی cPanel بدون SSH، با بررسی پیش‌نیاز و قفل نصب. |
| فونت | Vazirmatn آفلاین به‌عنوان پیش‌فرض؛ فونت‌های مجاز قابل مدیریت از پنل. |
| احراز هویت MVP | کارکنان با نام کاربری/موبایل و رمز؛ بیمار با موبایل و کد ملی تا زمان تغییر سیاست. |
| Queue/Cron | Cron cPanel برای اعلان، بکاپ، اقساط، پاک‌سازی و کارهای زمان‌دار؛ اجرای تکراری با قفل اتمیک. |
| API آینده | مرزهای سرویس و Provider/Adapter از ابتدا مشخص؛ API عمومی در MVP فعال نیست. |

## 2. اصول مهندسی

کد بر اساس جداسازی مسئولیت‌ها، وابستگی معکوس، نام‌گذاری صریح، اعتبارسنجی در مرز ورودی، سرویس‌های کاربردی کوچک، Policyهای سروری و تست‌پذیری طراحی می‌شود. مدل‌های Eloquent نباید محل اجرای منطق پیچیدهٔ کسب‌وکار باشند؛ منطق کاربردی در Action/Service و قواعد دسترسی در Policy/Permission نگهداری می‌شود.

اصلاح سریع و کم‌خطر بر ساختارهای هوشمند اما شکننده مقدم است. قابلیت‌های خارج از MVP ساخته نمی‌شوند، اما نقاط اتصال آینده مانند IPPanel، درگاه پرداخت، API، Webhook و ذخیره‌سازی جایگزین با Interface طراحی می‌شوند.

## 3. ساختار لایه‌ای پیشنهادی

```text
app/
├── Actions/             # عملیات کاربردی با یک ورودی مشخص
├── Console/             # فرمان‌ها و کارهای Cron
├── Domain/              # Enumها، Value Objectها، قراردادهای دامنه
├── Events/              # رویدادهای قابل ممیزی و اعلان
├── Exceptions/          # خطاهای دامنه و خطاهای قابل پیگیری
├── Http/
│   ├── Controllers/     # کنترلرهای سبک
│   ├── Middleware/      # Tenant، امنیت، ورود و محدودیت نرخ
│   ├── Requests/        # اعتبارسنجی فرم و درخواست
│   └── Resources/       # قرارداد خروجی آینده
├── Jobs/                # کارهای زمان‌دار و صفی
├── Models/              # مدل‌های دادهٔ سبک
├── Notifications/       # کانال داخلی و Adapterهای آینده
├── Policies/            # مجوزهای سطح سرور
├── Providers/           # اتصال‌های قابل تعویض
├── Queries/             # Queryهای خواندنی و بهینه
├── Services/            # سرویس‌های چندمرحله‌ای
└── Support/             # ابزارهای عمومی، تاریخ، اعداد و خروجی
```

در `resources/views`، مسیرهای `layouts`، `components`، `forms`، `tables` و `pages` جدا می‌شوند. تمام صفحه‌های مدیریتی باید از کامپوننت‌های مشترک جدول، فرم، فیلتر، وضعیت، اعلان و مودال استفاده کنند.

## 5. مدل چندمستاجری

هر جدول متعلق به یک کلینیک باید `tenant_id`، ایندکس ترکیبی مناسب و Scope اجباری داشته باشد. جدول‌های سراسری مانند `users`، `tenants`، `permissions` و `system_settings` استثناهای مستند هستند. سوپرادمین برای مشاهدهٔ Tenant باید از مسیر صریح Impersonation/Support Access عبور کند؛ این مسیر علت، شروع، پایان و عملیات انجام‌شده را ثبت می‌کند.

الگوی دسترسی:

```text
Request
  -> Authenticate
  -> Resolve active tenant
  -> Authorize permission/policy
  -> Apply tenant scope
  -> Execute action/query
  -> Audit sensitive operation
```

هیچ کنترل‌کننده، Job، Exporter یا Query نباید Tenant را از پارامتر خام کاربر قبول کند. Tenant فعال باید از عضویت معتبر، نشست امن یا مسیر پشتیبانی سوپرادمین resolve شود.

## 6. طراحی احراز هویت و مجوز

مجوزها با کلیدهای پایدار مانند `patients.view`، `patients.create`، `patients.update`، `patients.archive`، `patients.print` و `patients.export` ذخیره می‌شوند. نقش پیش‌فرض فقط مقدار اولیه است؛ مجوز نهایی از ترکیب نقش، دسترسی اختصاصی کاربر، Tenant، شعبه و دامنهٔ داده محاسبه می‌شود.

برای بیمار، فعال‌سازی حساب توسط منشی انجام می‌شود. تغییر اطلاعات حساس بیمار در MVP به صف تأیید منشی می‌رود. عملیات حذف/بایگانی، مشاهدهٔ پروندهٔ حساس، خروجی و ورود پشتیبانی به ممیزی نیاز دارند.

## 7. استقرار cPanel

بستهٔ انتشار باید شامل `vendor/` باشد تا نصب روی هاست بدون SSH ممکن شود. ویزارد نصب مسیر زیر را اجرا می‌کند:

1. نمایش توافق و بررسی PHP 8.2/8.3، افزونه‌ها، حافظه و مجوز پوشه‌ها.
2. دریافت مشخصات MySQL و انجام اتصال آزمایشی.
3. ساخت `.env` یا تنظیمات معادل بدون نمایش رمز پس از ذخیره.
4. ساخت کلید برنامه و تنظیم منطقهٔ زمانی.
5. اجرای Migration و Seeder هسته.
6. ساخت اولین سوپرادمین.
7. تنظیم نام محصول، برند، لوگو و فونت پیش‌فرض.
8. نوشتن قفل نصب و حذف/مسدودکردن مسیر نصب.
9. نمایش دستورهای Cron و چک سلامت نصب.

## 8. قراردادهای کیفیت

هر Pull Request یا Commit قابل تحویل باید با تست‌های مربوط، توضیح تغییر، اثر امنیتی، Migration/rollback و دستور بازتولید همراه باشد. فایل‌های زبان، تنظیمات و متن‌های رابط نباید به‌صورت پراکنده در Viewها hard-code شوند.
